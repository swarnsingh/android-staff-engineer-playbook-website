# Kotlin 2.4 Update for Android and KMP

## Overview

Kotlin 2.4 is important for Android and Kotlin Multiplatform teams because it is not only a language release. It changes the KMP interop story: Swift export is now Alpha, and `kotlinx.coroutines.flow.Flow` can be exported to Swift as `AsyncSequence` out of the box with type information preserved.

For Android-only teams, the release is still relevant because it stabilizes language and standard-library features that affect API design, code generation, annotation processing, and build compatibility.

## Highest-Impact Changes

| Area | Kotlin 2.4 change | Why Android/KMP engineers care |
|---|---|---|
| Language | Context parameters are Stable, except explicit context arguments and callable references | Safer dependency/context passing for DSLs and domain APIs |
| Language | Explicit backing fields are Stable | Cleaner custom property storage without separate private fields |
| Annotation targets | New defaulting rules and `@all` meta-target are Stable | Less error-prone annotations for serialization, DI, validation, and Java interop |
| Standard library | `kotlin.uuid.Uuid` is Stable | Common UUID type for Android, iOS, backend, and shared code |
| Standard library | Sorted-order helpers like `isSorted()` | Cheaper validation without sorting copies |
| JVM | Java 26 target support and annotations in metadata enabled by default | Tooling, annotation processors, and metadata readers see richer Kotlin information |
| Native | Swift package dependencies | KMP modules can depend on Swift packages more directly |
| Native | Swift export is Alpha | Direct Swift-facing APIs become a real migration path, not just future theory |
| Native/coroutines | Flow export to Swift `AsyncSequence` enabled by default | Shared `Flow<T>` APIs can be consumed idiomatically in Swift |
| Native runtime | CMS GC enabled by default | Better default memory behavior for Kotlin/Native apps |
| Gradle | Gradle 9.5 compatibility | Build upgrades can move forward with the Kotlin plugin |

## Language Features

### Context parameters are Stable

Context parameters let APIs require contextual values without passing them through every call manually.

```kotlin
context(tracer: Tracer)
suspend fun CheckoutService.submit(order: Order): Receipt {
    tracer.span("checkout.submit")
    return submitInternal(order)
}
```

Staff-level guidance:

- Good for cross-cutting context in constrained domains: tracing, localization, formatting, policy objects.
- Risky when used as invisible dependency injection. Readers still need to know where the context comes from.
- Avoid making core business logic depend on a large ambient context object.

### Explicit backing fields are Stable

Explicit backing fields let a property define storage directly.

```kotlin
class Session {
    var token: String?
        field = null
        private set

    fun authenticate(newToken: String) {
        token = newToken
    }
}
```

This reduces boilerplate for properties that need custom access while preserving a real backing field.

### Annotation target improvements

Kotlin annotations often have to land on the correct JVM element: field, getter, setter, parameter, or property. Kotlin 2.4 stabilizes improvements that reduce surprises and adds stronger property-wide targeting.

Why this matters on Android:

- DI annotations must land where Hilt/Dagger expects them.
- Serialization annotations must land where the serializer reads them.
- Room and validation annotations often depend on field/getter placement.
- Java interop libraries may ignore Kotlin-only property metadata.

Staff-level guidance: when an annotation affects generated code or reflection, verify the generated bytecode/metadata or compiler output during framework upgrades.

## Standard Library

### Stable `Uuid`

`kotlin.uuid.Uuid` being Stable is a major KMP quality-of-life improvement. Shared modules no longer need string-only IDs or expect/actual wrappers for common UUID representation, parsing, and comparison. The random V4/V7 generation helpers still require experimental opt-in, so teams should centralize ID generation behind an app-owned factory.

```kotlin
data class ClientRequestId(val value: Uuid)
```

For distributed mobile systems, UUIDs commonly back:

- Idempotency keys.
- Client-created entity IDs.
- Offline outbox operation IDs.
- Trace correlation IDs.

Use UUIDs deliberately. A random ID is not a replacement for a domain idempotency contract, but it is a good primitive for one.

### Sorted-order checks

Kotlin 2.4 adds helpers for checking sorted order without sorting.

```kotlin
check(messages.isSortedBy { it.createdAt })
```

This is useful in tests and defensive checks where sorting would hide an upstream ordering bug.

## Kotlin/Native and Swift Export

### Swift export is Alpha

Swift export generates Swift-facing APIs more directly than the Objective-C bridge. In Kotlin 2.4 it is officially Alpha, which means it is meaningful enough to evaluate but not yet a default production assumption for every app.

Staff-level guidance:

- Evaluate it in a sample module before promising migration.
- Keep public KMP APIs boring: simple value types, explicit names, predictable errors.
- Avoid exposing experimental Kotlin language features across the Swift boundary unless the iOS team agrees.
- Keep existing Objective-C bridge/SKIE wrappers where the production risk is lower.

### Flow exports to Swift `AsyncSequence`

Kotlin 2.4 adds built-in export of `kotlinx.coroutines` Flow types to Swift `AsyncSequence`.

Kotlin:

```kotlin
class ProfileViewModel {
    val state: StateFlow<ProfileState> = repository.observeProfile()
        .stateIn(scope, SharingStarted.WhileSubscribed(5_000), ProfileState.Loading)
}
```

Swift:

```swift
Task {
    do {
        for try await state in viewModel.state.asAsyncSequence() {
            self.state = state
        }
    } catch is CancellationError {
        // Normal task cancellation.
    } catch {
        // Surface as state or telemetry.
    }
}
```

Important details:

- Type information is preserved for public Flow APIs.
- The feature is enabled by default in Swift export.
- Exported suspend functions become Swift `async` counterparts.
- By default, exported suspend and Flow code runs with a Kotlin coroutine context using `Dispatchers.Default`.
- If code must run on Main, switch in Kotlin with `withContext(Dispatchers.Main)`.

This changes the KMP recommendation. SKIE and manual wrappers are no longer the only way to expose Flow to Swift, but Swift export is still Alpha. Production teams should choose based on stability, generated API quality, and iOS team experience.

## Migration Review Checklist

Before upgrading a serious Android/KMP codebase to Kotlin 2.4:

- Confirm Android Gradle Plugin and Compose compiler compatibility.
- Confirm all compiler plugins support Kotlin 2.4: KSP, Room, Hilt/Dagger, serialization, Compose, SKIE, SQLDelight, Ktor plugins.
- Run binary compatibility checks for published libraries.
- Inspect generated APIs for KMP public modules.
- Run iOS framework generation in CI.
- Test Flow collection from Swift if using Swift export.
- Verify annotation processors after annotation target defaulting changes.
- Audit custom Gradle convention plugins for Kotlin plugin API changes.
- Keep a rollback plan for compiler/plugin mismatches.

## Staff Engineer Guidance

Kotlin 2.4 is a good upgrade candidate when the dependency graph is ready. The biggest architectural opportunity is KMP API cleanup: shared ViewModels and repositories can expose Flow in a way Swift can consume more naturally.

Do not upgrade only because the language feature list is exciting. Upgrade when:

- The compiler/plugin matrix is green.
- Build cache and CI times are measured before/after.
- Generated Swift APIs are reviewed by iOS engineers.
- Coroutine and Flow interop is covered by integration tests.
- Public library APIs are checked for binary/source compatibility.
