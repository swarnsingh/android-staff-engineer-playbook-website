# Compose Multiplatform (CMP)

> Jetpack Compose transformed Android UI from imperative XML to declarative state functions. Compose Multiplatform (CMP), developed by JetBrains, takes the *exact same Compose compiler and runtime* and targets iOS, Desktop, and Web. On iOS, CMP does not use UIKit — it renders every pixel via the **Skia** graphics engine inside a single `UIViewController`. A Staff engineer must understand this rendering architecture, its implications for accessibility and platform fidelity, and when to mix CMP screens with native SwiftUI screens.

---

## Overview

### How CMP Renders on Each Platform

| Platform | Rendering Engine | UI Framework Used | Native Feel |
|---|---|---|---|
| Android | Android Canvas → RenderNode → GPU | Jetpack Compose (native to the OS) | 100% native |
| iOS | **Skia (C++) → Metal GPU** | Nothing from UIKit | 95% native (scrolling, text selection slightly off) |
| Desktop (JVM) | Skia → OpenGL/Metal | Nothing from AWT/Swing | 90% native |
| Web (Wasm) | Skia → WebGL Canvas | Nothing from DOM | 85% native |

### The iOS Rendering Pipeline

```text
@Composable fun CheckoutScreen() { ... }
         │
         ▼
[Compose Compiler Plugin]
    Transforms @Composable functions into a Slot Table (node tree)
         │
         ▼
[Compose Runtime]
    Manages recomposition, side effects, state snapshots
    (IDENTICAL to Android — same code runs on both platforms)
         │
         ▼
[Compose UI (Layout + Drawing)]
    Measures, places, and draws nodes
         │
         ▼
[Skia Backend (iOS-specific)]
    Translates Canvas draw commands to Skia C++ calls
    Skia renders to a Metal texture
         │
         ▼
[CAMetalLayer inside a UIViewController]
    The Metal texture is displayed on screen
    iOS sees a single opaque UIView — NOT individual UIKit elements
```

**Critical implication:** iOS VoiceOver, Dynamic Type, and system-wide text selection cannot "see inside" the Skia canvas. CMP must explicitly build accessibility bridges that translate Compose Semantics into a virtual UIKit accessibility tree.

## 1. What Feels Different on iOS

### Scrolling Physics
iOS users expect a specific deceleration curve and rubber-banding behavior when scrolling. UIKit's `UIScrollView` implements this with Apple's proprietary physics engine. CMP's `LazyColumn` implements its own scrolling physics in Kotlin.

JetBrains has invested heavily in matching iOS scrolling feel (as of CMP 1.6+, the match is very close), but hyper-sensitive iOS users may notice:
- Slightly different overscroll bounce amplitude.
- Different velocity curves when flinging quickly.
- Different behavior when scrolling hits a nested scrollable element.

### Text Selection
iOS native text selection uses a magnifying glass loupe, haptic feedback, and smart word-boundary snapping. CMP implements its own text selection handles in Skia, which feel slightly different from iOS native.

### Keyboard Handling
iOS keyboard avoidance (shifting content up when the keyboard appears) is managed by UIKit's `UIResponder` chain. CMP must intercept keyboard notifications and manually adjust the Compose layout — which can lag behind the keyboard animation by 1-2 frames.

### Navigation Gestures
iOS's back-swipe gesture (swiping from the left edge to go back) is intercepted at the `UINavigationController` level. CMP does not use `UINavigationController` — it implements its own navigation in Compose. The back-swipe gesture must be manually reimplemented.

## 2. Mixing CMP and Native SwiftUI

Because CMP on iOS is just a `UIViewController`, you can freely mix CMP screens with native SwiftUI views.

### Embedding CMP Inside SwiftUI

```swift
// iosApp/ComposeCheckoutView.swift

import SwiftUI
import SharedCode  // The KMP framework

struct ComposeCheckoutView: UIViewControllerRepresentable {
    func makeUIViewController(context: Context) -> UIViewController {
        // MainViewControllerKt is generated by the CMP framework
        return MainViewControllerKt.CheckoutViewController()
    }
    
    func updateUIViewController(_ uiViewController: UIViewController, context: Context) {
        // Called when SwiftUI state changes — use to pass data to Compose
    }
}

// Usage in a SwiftUI navigation stack
struct AppView: View {
    var body: some View {
        NavigationStack {
            VStack {
                // Native SwiftUI home screen
                HomeScreen()
                
                NavigationLink("Go to Checkout") {
                    // Embedded CMP screen
                    ComposeCheckoutView()
                        .ignoresSafeArea(.keyboard)
                        .navigationBarHidden(true)
                }
            }
        }
    }
}
```

### Embedding Native UIKit Inside CMP

If CMP's implementation of a specific component is inadequate (e.g., maps, camera previews, or web views), you can embed native UIKit views inside Compose:

```kotlin
// shared/src/iosMain/kotlin/com/example/ui/PlatformMapView.kt

@OptIn(ExperimentalForeignApi::class)
@Composable
actual fun MapView(
    latitude: Double,
    longitude: Double,
    zoomLevel: Float,
    modifier: Modifier
) {
    UIKitView(
        factory = {
            val mapView = MKMapView()
            val region = MKCoordinateRegion(
                center = CLLocationCoordinate2DMake(latitude, longitude),
                span = MKCoordinateSpan(
                    latitudeDelta = 0.01 / zoomLevel,
                    longitudeDelta = 0.01 / zoomLevel
                )
            )
            mapView.setRegion(region, animated = false)
            mapView.showsUserLocation = true
            mapView
        },
        modifier = modifier,
        update = { mapView ->
            // Called on recomposition — update the map center
            val region = MKCoordinateRegion(
                center = CLLocationCoordinate2DMake(latitude, longitude),
                span = mapView.region.span
            )
            mapView.setRegion(region, animated = true)
        }
    )
}

// shared/src/androidMain/kotlin/com/example/ui/PlatformMapView.kt
@Composable
actual fun MapView(
    latitude: Double,
    longitude: Double,
    zoomLevel: Float,
    modifier: Modifier
) {
    // Use Google Maps Compose library on Android
    GoogleMap(
        modifier = modifier,
        cameraPositionState = rememberCameraPositionState {
            position = CameraPosition.fromLatLngZoom(
                LatLng(latitude, longitude),
                zoomLevel
            )
        }
    )
}
```

### The `expect`/`actual` @Composable Pattern

For components that differ between platforms, use `expect`/`actual` on `@Composable` functions:

```kotlin
// commonMain
@Composable
expect fun PlatformDatePicker(
    selectedDate: Long,
    onDateSelected: (Long) -> Unit,
    modifier: Modifier
)

// androidMain — uses Material3 DatePicker
@Composable
actual fun PlatformDatePicker(
    selectedDate: Long,
    onDateSelected: (Long) -> Unit,
    modifier: Modifier
) {
    val datePickerState = rememberDatePickerState(initialSelectedDateMillis = selectedDate)
    DatePicker(state = datePickerState, modifier = modifier)
    LaunchedEffect(datePickerState.selectedDateMillis) {
        datePickerState.selectedDateMillis?.let(onDateSelected)
    }
}

// iosMain — uses UIDatePicker via UIKitView
@Composable
actual fun PlatformDatePicker(
    selectedDate: Long,
    onDateSelected: (Long) -> Unit,
    modifier: Modifier
) {
    UIKitView(
        factory = {
            UIDatePicker().apply {
                datePickerMode = UIDatePickerMode.UIDatePickerModeDate
                preferredDatePickerStyle = UIDatePickerStyle.UIDatePickerStyleInline
            }
        },
        modifier = modifier
    )
}
```

## 3. Navigation in CMP

### The Problem
On Android, Compose Navigation uses `NavHost` with `composable()` destinations. On iOS, there is no Android-specific navigation infrastructure.

### The Solution: Compose Navigation is Multiplatform
JetBrains has made `androidx.navigation:navigation-compose` work on CMP (experimental). You can use the same `NavHost` pattern on all platforms:

```kotlin
// commonMain
@Composable
fun AppNavigation() {
    val navController = rememberNavController()
    
    NavHost(navController = navController, startDestination = "home") {
        composable("home") {
            HomeScreen(
                onProductClick = { productId ->
                    navController.navigate("product/$productId")
                }
            )
        }
        composable("product/{id}") { backStackEntry ->
            val productId = backStackEntry.arguments?.getString("id") ?: return@composable
            ProductDetailScreen(
                productId = productId,
                onBack = { navController.popBackStack() }
            )
        }
        composable("checkout") {
            CheckoutScreen(
                onOrderComplete = {
                    navController.navigate("home") {
                        popUpTo("home") { inclusive = true }
                    }
                }
            )
        }
    }
}
```

## 4. Performance Considerations

### Binary Size Impact

CMP on iOS embeds the Skia rendering engine inside the `.xcframework`. This adds significant size:

| Component | Binary Size Impact |
|---|---|
| Shared business logic only (no CMP) | ~2-5 MB |
| CMP with Skia (full UI sharing) | **~10-15 MB** |
| CMP + Compose Resources (fonts, images) | ~15-25 MB |

### Rendering Performance

CMP renders via Metal on iOS (modern devices). On older devices without Metal (iPhone 5s and earlier — effectively irrelevant now), CMP falls back to OpenGL ES, which is significantly slower.

On modern iPhones (A12+ chips), CMP achieves:
- 60 FPS for standard scrolling and transitions.
- Occasional frame drops during complex animations with >100 nodes.
- Layout measurement is O(n) where n = number of Composable nodes, identical to Android.

### Memory Overhead

CMP on iOS uses more memory than a pure SwiftUI app:
- **Skia context:** ~15-30 MB of GPU memory.
- **Compose Slot Table:** ~5-10 MB for a typical screen tree.
- **Total additional overhead:** ~20-40 MB vs pure SwiftUI.

For an app with a 200 MB memory budget, this is acceptable. For an iOS widget or a lightweight extension, it's too heavy.

## Common Pitfalls

### 1. The `UIKitView` Scroll Conflict
If you embed a `UIKitView` (e.g., `MKMapView`) inside a `LazyColumn`, both the map and the LazyColumn will compete for scroll gestures. The user tries to scroll the map but the list scrolls instead.

**Fix:** Use `Modifier.nestedScroll` to coordinate between the CMP scroller and the embedded UIKit view.

### 2. The Safe Area Insets
iOS has notches, home indicators, and dynamic islands. CMP must respect these safe areas. Use `WindowInsets` in your Compose code:

```kotlin
Scaffold(
    modifier = Modifier.windowInsetsPadding(WindowInsets.systemBars)
) { paddingValues ->
    // Content respects notch and home indicator
}
```

### 3. The Status Bar Color
On Android, you control the status bar color via `WindowCompat`. On iOS via CMP, you must configure it through the `UIViewController`'s `preferredStatusBarStyle`, which requires platform-specific code.
