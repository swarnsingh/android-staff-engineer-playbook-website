# Persistence in KMP

> Android engineers default to Room (SQLite) and DataStore (key-value). Both depend on Android-specific APIs (`android.database.sqlite.SQLiteOpenHelper`, `android.content.Context`). In KMP, you must replace them with SQLDelight (relational), Multiplatform Settings (key-value), or the new KMP-capable DataStore. A Staff engineer must understand not just the API differences, but the architectural shift — SQLDelight generates Kotlin from SQL (the inverse of Room), and Multiplatform Settings wraps fundamentally different iOS storage backends.

---

## Overview

| Domain | Android (JVM) | KMP Replacement | Architectural Difference |
|---|---|---|---|
| Relational DB | Room | **SQLDelight** | Room: Kotlin annotations → generate SQL. SQLDelight: SQL files → generate Kotlin |
| Key-Value | SharedPreferences / DataStore Preferences | **Multiplatform Settings** | Wraps `SharedPreferences` on Android, `NSUserDefaults` on iOS |
| Typed Key-Value | DataStore Proto | **DataStore KMP** (official) | Uses Okio for cross-platform file I/O |
| Document DB | Realm (Java) | **Realm Kotlin SDK** | Official KMP SDK by MongoDB |

## 1. SQLDelight (The Room Replacement)

### The Paradigm Inversion

**Room:** You write Kotlin DAOs with annotations. Room's KSP processor generates the SQL and the database helper code.

**SQLDelight:** You write `.sq` files containing raw SQL. SQLDelight's Gradle plugin generates typesafe Kotlin interfaces.

This inversion matters for KMP because SQL is platform-agnostic — the same `CREATE TABLE` statement works on Android's SQLite and iOS's SQLite. Room's annotation processing generates JVM-specific code that can't compile on iOS.

### Setting Up SQLDelight

**Dependencies (`build.gradle.kts`):**
```kotlin
plugins {
    alias(libs.plugins.sqldelight)
}

sqldelight {
    databases {
        create("AppDatabase") {
            packageName.set("com.example.db")
            // Generate Flow extensions for reactive queries
            generateAsync.set(true)
        }
    }
}

kotlin {
    sourceSets {
        androidMain.dependencies {
            implementation(libs.sqldelight.android.driver)
        }
        iosMain.dependencies {
            implementation(libs.sqldelight.native.driver)
        }
        commonMain.dependencies {
            implementation(libs.sqldelight.coroutines.extensions)
        }
    }
}
```

### Writing the Schema (`.sq` File)

```sql
-- shared/src/commonMain/sqldelight/com/example/db/Product.sq

-- 1. Schema Definition
CREATE TABLE Product (
    id TEXT NOT NULL PRIMARY KEY,
    name TEXT NOT NULL,
    description TEXT,
    price_cents INTEGER NOT NULL,
    currency TEXT NOT NULL DEFAULT 'USD',
    category TEXT NOT NULL,
    image_url TEXT,
    created_at INTEGER NOT NULL,     -- epoch millis
    updated_at INTEGER NOT NULL,
    is_active INTEGER AS Boolean NOT NULL DEFAULT 1  -- SQLDelight Boolean adapter
);

CREATE INDEX idx_product_category ON Product(category);
CREATE INDEX idx_product_active ON Product(is_active, category);

-- 2. Named Queries (SQLDelight generates Kotlin functions for each)

getProductById:
SELECT * FROM Product WHERE id = ?;

getProductsByCategory:
SELECT * FROM Product
WHERE category = ? AND is_active = 1
ORDER BY created_at DESC
LIMIT ? OFFSET ?;

searchProducts:
SELECT * FROM Product
WHERE (name LIKE '%' || ? || '%' OR description LIKE '%' || ? || '%')
AND is_active = 1
ORDER BY name ASC;

getProductCount:
SELECT COUNT(*) FROM Product WHERE is_active = 1;

-- 3. Mutations

insertProduct:
INSERT OR REPLACE INTO Product(
    id, name, description, price_cents, currency,
    category, image_url, created_at, updated_at, is_active
) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?);

deleteProduct:
DELETE FROM Product WHERE id = ?;

deactivateProduct:
UPDATE Product SET is_active = 0, updated_at = ? WHERE id = ?;

deleteAllProducts:
DELETE FROM Product;
```

### Generated Kotlin API

SQLDelight generates a `ProductQueries` class with typesafe functions:

```kotlin
// AUTO-GENERATED by SQLDelight — do NOT edit

interface ProductQueries : TransacterImpl {
    fun getProductById(id: String): Query<Product>
    fun getProductsByCategory(category: String, limit: Long, offset: Long): Query<Product>
    fun searchProducts(query: String, query_: String): Query<Product>
    fun getProductCount(): Query<Long>
    
    fun insertProduct(
        id: String, name: String, description: String?,
        price_cents: Long, currency: String, category: String,
        image_url: String?, created_at: Long, updated_at: Long,
        is_active: Boolean
    )
    fun deleteProduct(id: String)
    fun deactivateProduct(updated_at: Long, id: String)
    fun deleteAllProducts()
}
```

### Using SQLDelight with Flow (Reactive Queries)

```kotlin
// shared/src/commonMain/kotlin/com/example/data/ProductRepository.kt

class ProductRepository(private val database: AppDatabase) {
    
    // Reactive query — emits a new list every time the Product table changes
    fun observeProducts(category: String): Flow<List<Product>> {
        return database.productQueries
            .getProductsByCategory(category, limit = 50, offset = 0)
            .asFlow()
            .mapToList(Dispatchers.IO)
    }
    
    // One-shot query
    suspend fun getProduct(id: String): Product? {
        return withContext(Dispatchers.IO) {
            database.productQueries
                .getProductById(id)
                .executeAsOneOrNull()
        }
    }
    
    // Transaction — atomic multi-statement operation
    suspend fun syncProducts(products: List<ProductDto>) {
        withContext(Dispatchers.IO) {
            database.transaction {
                database.productQueries.deleteAllProducts()
                products.forEach { dto ->
                    database.productQueries.insertProduct(
                        id = dto.id,
                        name = dto.name,
                        description = dto.description,
                        price_cents = dto.priceCents,
                        currency = dto.currency,
                        category = dto.category,
                        image_url = dto.imageUrl,
                        created_at = dto.createdAt,
                        updated_at = dto.updatedAt,
                        is_active = dto.isActive
                    )
                }
            }
        }
    }
}
```

### The Driver Injection (Platform Boundary)

SQLDelight's `SqlDriver` is the platform-specific component:

```kotlin
// shared/src/androidMain/kotlin/com/example/db/DriverFactory.kt
import app.cash.sqldelight.driver.android.AndroidSqliteDriver

class AndroidDriverFactory(private val context: Context) {
    fun create(): SqlDriver {
        return AndroidSqliteDriver(
            schema = AppDatabase.Schema,
            context = context,
            name = "app.db",
            callback = object : AndroidSqliteDriver.Callback(AppDatabase.Schema) {
                override fun onOpen(db: SupportSQLiteDatabase) {
                    db.execSQL("PRAGMA journal_mode=WAL")  // Write-ahead logging
                    db.execSQL("PRAGMA foreign_keys=ON")
                }
            }
        )
    }
}
```

```kotlin
// shared/src/iosMain/kotlin/com/example/db/DriverFactory.kt
import app.cash.sqldelight.driver.native.NativeSqliteDriver

class IOSDriverFactory {
    fun create(): SqlDriver {
        return NativeSqliteDriver(
            schema = AppDatabase.Schema,
            name = "app.db"
        )
    }
}
```

### Database Migrations

SQLDelight handles migrations via numbered `.sqm` files:

```sql
-- shared/src/commonMain/sqldelight/migrations/1.sqm
-- Migration from version 1 to version 2

ALTER TABLE Product ADD COLUMN rating REAL;
ALTER TABLE Product ADD COLUMN review_count INTEGER NOT NULL DEFAULT 0;
```

```sql
-- shared/src/commonMain/sqldelight/migrations/2.sqm
-- Migration from version 2 to version 3

CREATE TABLE Favorite (
    user_id TEXT NOT NULL,
    product_id TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    PRIMARY KEY (user_id, product_id),
    FOREIGN KEY (product_id) REFERENCES Product(id) ON DELETE CASCADE
);
```

The driver automatically runs pending migrations on app launch (both Android and iOS).

## 2. Multiplatform Settings (The SharedPreferences Replacement)

For simple key-value storage (user preferences, flags, tokens), a relational database is overkill.

### Setup

```kotlin
// commonMain.dependencies
implementation("com.russhwolf:multiplatform-settings:1.1.1")
implementation("com.russhwolf:multiplatform-settings-coroutines:1.1.1")
```

### Usage in `commonMain`

```kotlin
// shared/src/commonMain/kotlin/com/example/prefs/UserPreferences.kt

class UserPreferences(private val settings: Settings) {
    
    // Simple get/set
    var isDarkMode: Boolean
        get() = settings.getBoolean("DARK_MODE", defaultValue = false)
        set(value) = settings.putBoolean("DARK_MODE", value)
    
    var authToken: String?
        get() = settings.getStringOrNull("AUTH_TOKEN")
        set(value) {
            if (value != null) settings.putString("AUTH_TOKEN", value)
            else settings.remove("AUTH_TOKEN")
        }
    
    var onboardingCompleted: Boolean
        get() = settings.getBoolean("ONBOARDING_DONE", defaultValue = false)
        set(value) = settings.putBoolean("ONBOARDING_DONE", value)
    
    var lastSyncTimestamp: Long
        get() = settings.getLong("LAST_SYNC", defaultValue = 0L)
        set(value) = settings.putLong("LAST_SYNC", value)
    
    fun clearAll() {
        settings.clear()
    }
}
```

### Platform-Specific `Settings` Creation

```kotlin
// androidMain
val settings: Settings = SharedPreferencesSettings(
    context.getSharedPreferences("app_prefs", Context.MODE_PRIVATE)
)

// iosMain
val settings: Settings = NSUserDefaultsSettings(
    NSUserDefaults(suiteName = "com.example.app")
        ?: NSUserDefaults.standardUserDefaults
)
```

### Observable Settings (Reactive)

```kotlin
// With multiplatform-settings-coroutines
class UserPreferences(private val settings: ObservableSettings) {
    
    // Emits every time the value changes
    val isDarkModeFlow: Flow<Boolean> = settings.getBooleanFlow("DARK_MODE", false)
    
    val authTokenFlow: Flow<String?> = settings.getStringOrNullFlow("AUTH_TOKEN")
}
```

### Behavioral Differences Between Platforms

| Behavior | SharedPreferences (Android) | NSUserDefaults (iOS) |
|---|---|---|
| Storage format | XML file | Property list (plist) |
| Thread safety | Thread-safe (synchronized internally) | Thread-safe (Apple guarantees) |
| Max value size | ~1MB (practical limit) | Unlimited (but slow for large values) |
| Observation | `OnSharedPreferenceChangeListener` | `NSNotification` (KVO) |
| App Groups sharing | Not applicable | Can share across app extensions |
| Backup | Included in Android backup by default | Included in iCloud backup by default |
| Encryption | None; use a platform vault backed by Android Keystore | None; use Keychain for secrets |

**Staff Warning:** Do NOT store auth tokens in Multiplatform Settings in production. Use `expect/actual` to access the Android Keystore / iOS Keychain for sensitive data.

## 3. DataStore KMP (The Official Google Option)

Google officially made Jetpack DataStore multiplatform-capable (starting with DataStore 1.1.0). It uses **Okio** for cross-platform file I/O.

```kotlin
// commonMain
val dataStore: DataStore<Preferences> = createDataStore(
    producePath = { "app_preferences.preferences_pb" }
)

// Reading
val darkModeFlow: Flow<Boolean> = dataStore.data.map { prefs ->
    prefs[booleanPreferencesKey("dark_mode")] ?: false
}

// Writing
suspend fun setDarkMode(enabled: Boolean) {
    dataStore.edit { prefs ->
        prefs[booleanPreferencesKey("dark_mode")] = enabled
    }
}
```

### DataStore KMP vs Multiplatform Settings

| Factor | Multiplatform Settings | DataStore KMP |
|---|---|---|
| Backend on Android | `SharedPreferences` (system API) | Custom protobuf file (Okio) |
| Backend on iOS | `NSUserDefaults` (system API) | Custom protobuf file (Okio) |
| iOS native access | ✅ iOS can read `NSUserDefaults` directly in Swift | ❌ iOS cannot read DataStore's custom file format |
| Async API | Optional (coroutines extension) | Mandatory (everything is `suspend` / `Flow`) |
| Type safety | Basic (get/put with key strings) | Higher (typed `PreferencesKey<T>`) |
| Migration support | None | Built-in `SharedPreferences → DataStore` migration |

**Staff Recommendation:** If your iOS team needs to read preferences from Swift (e.g., in an iOS widget extension), use Multiplatform Settings. If all preference access goes through shared Kotlin code, DataStore KMP is slightly more type-safe.

## Probing Questions

1.  **SQLDelight vs Room:** Explain why SQLDelight inverts the paradigm (write SQL → generate Kotlin) rather than copying Room's approach (write Kotlin → generate SQL). What technical constraint makes Room's approach impossible for Kotlin/Native?
2.  **Reactive Queries:** When a `Product` row is updated via `insertProduct` (INSERT OR REPLACE), how does SQLDelight's `asFlow()` know to re-emit? What mechanism triggers the Flow emission on iOS vs Android?
3.  **Migration Safety:** Your `.sqm` migration adds a NOT NULL column without a DEFAULT value. What happens on Android when the migration runs? What happens on iOS? Is the behavior identical?
4.  **NSUserDefaults vs SharedPreferences:** An iOS engineer writes Swift code that directly reads `NSUserDefaults(suiteName: "com.example.app")` to get the `isDarkMode` key. Your Kotlin code uses Multiplatform Settings to write to the same suite. Does the iOS engineer see the Kotlin-written value? Why or why not?
5.  **DataStore on iOS:** DataStore KMP writes a custom `.preferences_pb` protobuf file to the iOS app's sandboxed filesystem. An iOS engineer wants to read a preference from an iOS Today Widget (App Extension). Can they? What architectural constraint blocks them?
