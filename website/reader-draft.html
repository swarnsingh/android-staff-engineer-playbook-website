BEGINNING

1. A profile screen that needs to keep moving

You tap a profile. The app needs a name and an avatar from two requests. You try to scroll while they load. Nothing moves. What went wrong?

The main thread handles UI work such as input and drawing. If it sits waiting inside a blocking operation, it cannot handle the next UI event. Starting more work on that same blocked thread does not fix the queue.

BLOCKING WAITThe thread is occupied.

Like waiting at an oven and doing nothing else until its timer rings.

SUSPENDING WAITThe task pauses; the thread can move on.

Like setting a timer and preparing another dish while the first one cooks.

A coroutine is a computation that can suspend and resume. Suspending means pausing that computation without keeping its thread occupied by the wait. It lets us express “wait for this result” while other work makes progress.

The need comes first.

Our goal is a responsive screen while requests are waiting. Coroutines help organise that work; they do not make slow network requests disappear.

suspend marks a function that may suspend. It does not promise that a call will actually pause, pick a background thread, or make blocking code safe. The kitchen analogy explains waiting, but threads still execute the real work.

Contract: Kotlin coroutines basics ↗. Prerequisites: synchronous and asynchronous work ↗.

Check your intuition: does suspend move the request off Main?

No. It permits suspension. The implementation must avoid blocking Main; a suspending API can still contain blocking calls. Next, we will separate overlapping waits from the question of where code executes.

The UI can keep moving. But must we finish the name request before starting the avatar?

BEGINNING → MECHANISM

2. Start independent work together

If the name waits for 500ms and the avatar for 800ms, starting the second only after the first finishes creates two waits in a row. If the requests are independent, we can overlap those waits.

async starts a child computation and returns a Deferred: a handle to its eventual result. await() obtains that result, suspending the caller if it is not ready. Start both children before awaiting their results.

The core ideaKotlin fragment · fetch functions supplied by the app
val name = async { fetchName() }
val avatar = async { fetchAvatar() }
val resolvedName = name.await()
val resolvedAvatar = avatar.await()
Predict → run → change one thing

Run with concurrent = true. Then set it to false. Compare when each request starts and when the final result appears, not just the returned text.

Open the complete runnable JVM experiment
ProfileExperiment.ktRunnable · Kotlin/JVM · kotlinx.coroutines
import kotlinx.coroutines.*
import kotlin.time.TimeSource

fun main() = runBlocking {
    // Console bridge only: never block Android's UI thread.
    val concurrent = true // Change to false, then run again.
    val start = TimeSource.Monotonic.markNow()
    fun log(message: String) = println(
        "${start.elapsedNow().inWholeMilliseconds}ms " +
        "[${Thread.currentThread().name}] $message"
    )
    suspend fun fetchName(): String {
        log("name: start")
        delay(500)
        log("name: done")
        return "Ada"
    }
    suspend fun fetchAvatar(): String {
        log("avatar: start")
        delay(800)
        log("avatar: done")
        return "avatar.png"
    }
    val profile = coroutineScope {
        if (concurrent) {
            val name = async { fetchName() }
            val avatar = async { fetchAvatar() }
            val resolvedName = name.await()
            val resolvedAvatar = avatar.await()
            "$resolvedName · $resolvedAvatar"
        } else {
            val resolvedName = fetchName()
            val resolvedAvatar = fetchAvatar()
            "$resolvedName · $resolvedAvatar"
        }
    }
    log("profile: $profile")
}

runBlocking is the console bridge that keeps this ordinary main() alive until the work finishes. Its calling thread is blocked from returning; its default event loop can still run the children’s continuations. This is a JVM experiment, not an Android UI entry point. Read its contract ↗.

MECHANISM

3. Choose where the real work runs

Suspension does not make decoding a huge image cheap, and it cannot turn a blocking file read into a non-blocking operation. We need a second decision: which execution resources should handle each part?

A dispatcher determines how coroutine execution is scheduled. A coroutine’s context also carries other elements, such as its Job and a diagnostic name. Changing a dispatcher changes where work runs; it does not automatically make that work cancellable.

Work in our profile flowUsual choiceReason
Update screen stateMainUI work belongs on the UI thread; keep it brief.
A blocking file or legacy network callIOKeep blocking waits off Main.
Substantial CPU workDefaultUse workers intended for computation.
An already main-safe suspending APIFollow that API’s contractNo automatic need to wrap every suspend call in IO.

The component that performs blocking work should make its function main-safe: safe to call from Main. The caller should not have to know its storage implementation.

Main-safe boundaryAndroid-shaped fragment · dependencies supplied by the app
class AvatarStore(
    private val io: CoroutineDispatcher,
    private val files: BlockingAvatarFiles
) {
    suspend fun read(id: String): ByteArray = withContext(io) {
        files.read(id) // Blocking API; off Main, still blocking here.
    }
}

Injecting the dispatcher makes the execution policy replaceable in tests. If cancellation must interrupt the underlying blocking call, define its cancellation mechanism too; a dispatcher switch alone is insufficient.

Guidance: Android coroutine best practices ↗.

We can now choose where work runs. But when a function pauses, what remembers where it should continue?

MECHANISM · UNDER THE HOOD

4. How a suspended function remembers its place

Ordinary code relies on the call stack while a function executes. A suspending computation needs a way to return control now and continue later without keeping that stack occupied by its wait.

The compiler supplies that bookkeeping. A suspend function accepts an additional Continuation parameter in its lowered calling convention. A continuation represents the rest of the computation and its context; it can be resumed with a result or failure.

The Kotlin we writeKotlin fragment · API supplied by the app
suspend fun greeting(): String {
    val name = api.fetchName()
    return "Hello, $name"
}
Follow the continuation parameter and state labels

A state machine stores a resume position and values needed later. If a call suspends, it returns COROUTINE_SUSPENDED; if it completes immediately, execution continues with its value. A suspend call is a possible suspension point.

A deliberately simplified Java-shaped viewPseudocode · not runnable or exact decompiler output
Object greeting(Continuation<? super String> completion) {
    GreetingState state = obtainOrReuseState(completion);
    switch (state.label) {
        case 0:
            state.label = 1; // Resume after fetchName.
            Object value = api.fetchName(state);
            if (value == COROUTINE_SUSPENDED) {
                return COROUTINE_SUSPENDED;
            }
            return "Hello, " + value;
        case 1:
            throwIfFailure(state.result);
            return "Hello, " + state.result;
        default:
            throw invalidResumeState();
    }
}
  1. On a fresh call, the state selects the first part of the function.
  2. Before the suspending call, the next label is recorded and needed locals can be saved in fields.
  3. If it suspends, control returns. Later, resumption supplies the result or failure and reaches the saved state.

Real generated code also handles continuation reuse, exception paths, and backend-specific details. Some tail-call or inline cases avoid a separate state machine. Inspecting a decompiler is useful, but field names, label counts, and allocations are not universal promises.

Validate the model against the language specification ↗, Continuation API ↗, and JVM compiler lowering ↗. A reading companion is Dove Letter’s compiler walkthrough ↗.

That explains resumption, not ownership. A saved continuation does not decide whether the profile is still wanted. We need an explicit lifetime for the work.

MECHANISM · SEE IT HAPPEN

5. Ownership and the job tree

A scope provides the context in which coroutines are started. A Job represents lifecycle, completion, and cancellation. A child coroutine has its own Job linked to its parent; a scope’s Job can also be a lifetime container rather than a running coroutine.

Our coroutineScope groups the two requests: it returns only when its block and children finish. A required child’s failure cancels the group. This makes the boundary visible to the caller.

In an Android app, a UI state holder can start the load in viewModelScope. That scope is cancelled when its ViewModel is cleared. A screen merely becoming invisible does not always clear its ViewModel.

The app’s entry pointAndroid-shaped fragment · not runnable in the JVM playground
fun onProfileRequested() {
    viewModelScope.launch {
        // loadProfile owns the group of request children.
        state.value = loadProfile()
    }
}

MECHANISM · FAILURE AND CLEANUP

6. Cancellation is a request, then completion

Assume navigation pops the profile destination and clears its destination-scoped ViewModel. Its scope requests cancellation of the in-flight load. The request travels down to its children.

Cancellation is cooperative. The children in our example are waiting in cancellable delay calls, so cancellation can end those waits without waiting for their original deadlines. CPU-heavy loops need explicit checks such as ensureActive(). A blocking API needs its own cancellation or interruption strategy.

A Job can be cancelling while its children or cleanup are still finishing. Calling cancel() requests the stop; cancelAndJoin() also waits for completion.

Preserve the cancellation signalKotlin fragment · inside a suspending load
try {
    return api.fetchAvatar()
} catch (cancelled: CancellationException) {
    throw cancelled
} catch (failed: IOException) {
    return null // An expected optional-avatar failure.
} finally {
    responseHandle.close() // Non-suspending cleanup.
}

This fragment assumes an owned handle already exists. Use finally or an appropriate resource-management construct to release it. Necessary suspending cleanup after cancellation may need a narrowly scoped withContext(NonCancellable); do not use that as a general way to keep work alive.

Catching cancellation does not reactivate a cancelled Job. But swallowing the exception can let ordinary statements continue or disguise the outcome as success. Preserve the signal unless the API explicitly defines a local cancellation-to-result boundary.

Checkpoint: does leaving the screen always cancel the load?

No. In our chosen scenario, the destination is removed and its ViewModel is cleared, so its scope cancels the load and its children. A retained back-stack owner or a configuration change can keep the ViewModel alive. If work should stop on a different event, define and test that event explicitly.

Contracts: Android coroutine lifetimes ↗, cancelAndJoin ↗, and NonCancellable ↗.

Cancellation answers “who still wants this?” Failure asks a different question: must the whole profile fail if only the avatar fails?

MECHANISM → STAFF

7. Decide which failures belong together

If both results are required, coroutineScope gives us one failure boundary. A child’s failure cancels its siblings. Catching only around its await() does not undo the parent’s cancellation.

Suppose product instead chooses: name required, avatar optional. The screen can show an initial or placeholder when the avatar is unavailable. Now the code needs an explicit partial-result policy.

Required name, optional avatarKotlin fragment · Profile and main-safe api supplied by the app
suspend fun loadProfile(): Profile = supervisorScope {
    val name = async { api.fetchName() }
    val avatar = async {
        try {
            withTimeoutOrNull(1_000) { api.fetchAvatar() }
        } catch (cancelled: CancellationException) {
            throw cancelled
        } catch (failed: IOException) {
            null
        }
    }
    val resolvedName = name.await()
    val resolvedAvatar = avatar.await()
    Profile(resolvedName, resolvedAvatar)
}

The timeout supplies a fallback only for its own timeout, and still relies on cooperative cancellation; it is not a hard deadline for a blocking call. Cancellation from the owner still propagates. We handle the expected avatar I/O failure locally; unexpected failures remain failures. If the name fails, its await() escapes the scope block, which cancels the remaining work.

Supervision is isolation, not error handling.

Replacing the builder alone is not enough. An unhandled failure rethrown by await() can still escape the supervisor block and fail the load.

Checkpoint: is supervisorScope alone enough to render a partial profile?

No. It isolates child failure, but you must also decide how to consume each result. In this example an expected avatar failure becomes a nullable result, while cancellation and required-name failure still propagate. That is the behaviour the UI can build on.

Contract: supervisorScope ↗.

We have working mechanisms. A staff-level design makes their user-visible contract explicit and proves its failure behaviour.

STAFF DECISIONS

8. Turn the mechanism into a production contract

“We use coroutines” does not describe what the screen guarantees. Our worked decision is: load independent data concurrently; require the name; allow an avatar fallback after an expected failure or a one-second timeout; cancel with the declared owner.

DecisionChoice for this screenEvidence or revisit trigger
LifetimeThe destination-scoped ViewModel owns the load.Test owner clearing separately from rotation and temporary invisibility.
Failure contractName required; avatar may fall back.Test name failure, avatar failure, timeout, and external cancellation.
Resource budgetTwo requests for this load; a larger fan-out needs admission limits.Measure actual latency, battery/network costs, and duplicate loads.
ObservabilityDistinguish success, fallback, failure, and cancellation.Use bounded-cardinality outcomes; avoid treating every navigation cancellation as an incident.
DurabilityThis disposable read may be cancelled. A promised upload needs a separate durable design.An in-memory scope cannot guarantee work survives process death.

Use controlled test dispatchers and virtual time for ordering and timeout tests. Assert the result, sibling cancellation, and cleanup—not the elapsed wall-clock duration from a laptop playground. Inject execution dependencies where the production code owns them.

A photo upload introduces a new need: preserving a user’s accepted action when the process dies. At that point, evaluate durable scheduling, stored progress, retry safety, and idempotency. Simply moving the upload into a longer-lived coroutine scope does not provide persistence.

Apply it: we now prefetch profiles from a list. Who owns that work?

Start with the product promise. Is prefetch a disposable optimisation, a cache refresh shared by several screens, or promised durable work? Choose an owner and cancellation boundary that match that promise, then define deduplication, resource limits, and stale-result handling. A profile-screen scope is not automatically the right owner for all three.

We can now answer the opening problem: the screen remains responsive because waits do not occupy Main, independent requests overlap, optional failure has a defined fallback, and the chosen owner determines when the load is no longer needed.
