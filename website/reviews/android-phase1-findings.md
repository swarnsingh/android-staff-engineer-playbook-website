# Android Phase 1: possible errors in the original chapters

Found while writing the teaching layer for Android Phase 1 (the nine chapters under `android/architecture/` listed in Phase 1 of `android.md`). These are **findings for the owner's review**, not approved corrections. Nothing here is applied: the original Markdown is unchanged and no entry exists in `content/corrections-*.json`.

On the website, each finding is shown as an **Under review** note placed before the section that contains it. The note says the passage is under review, but the website does not print a replacement text next to the original. The teaching layer avoids restating these claims.

Sources were checked on 2026-10-25.

| ID | Chapter, section | Original says | Problem | Evidence |
|---|---|---|---|---|
| A1 | Activity, Internal Mechanics: The Lifecycle (and Answer Key 1) | Opening split-screen mode is an example of `onPause()` without `onStop()` | Android 10+ supports multi-resume, so entering split screen is not itself a reliable example of `onPause()`. The generic activity-lifecycle page still describes the older single-resumed model; the multi-window page explicitly documents the newer behaviour | [Multi-window support](https://developer.android.com/develop/ui/views/layout/support-multi-window-mode): "Android 10 (API level 29) and higher versions support multi-resume—all activities remain in the RESUMED state" |
| VM1 | ViewModel, Internal Mechanics | The Activity hands the `ViewModelStore` "to the OS", and the new Activity asks the OS for it back | The retained non-configuration instance stays in the app process; nothing is handed to the system. The chapter's own Answer Key 1 says this correctly | [ComponentActivity source](https://android.googlesource.com/platform/frameworks/support/+/435272fb9809ac8cf8ccd6c5782fb08ffb36f381/activity/activity/src/main/java/androidx/activity/ComponentActivity.kt), `onRetainNonConfigurationInstance()` and `ensureViewModelStore()`; [ViewModel overview](https://developer.android.com/topic/libraries/architecture/viewmodel) |
| SSH1 | SavedStateHandle, Tradeoffs | "`TransactionTooLargeException` limits (1MB across the *entire* OS IPC system)" | The 1MB Binder transaction buffer is per process, shared by that process's in-flight transactions; Android recommends keeping saved state under 50KB | [Parcelables and Bundles](https://developer.android.com/guide/components/activities/parcelables-and-bundles) |
| PD1 | Process Death, Tradeoffs | "IPC limit of 1MB total across all apps" | Same as SSH1: the limit is per process | Same as SSH1 |
| PD2 | Process Death, Staff Engineer Thinking, point 1 | Test process-death survival with "Don't keep activities" or by killing the process | "Don't keep activities" destroys activities but keeps the process, so it tests activity recreation, not process death. The chapter's own Answer Key 3 says so | Answer Key 3 of the same chapter; `adb shell am kill <package>` on a backgrounded app is the process-death path |
| MV1 | MVVM vs MVI, Compose Integration, point 2 | Avoid `{ vm.processIntent(it) }` because it "allocates a new lambda each composition" | Outdated for the default strong-skipping model: since Kotlin 2.0.20, Compose remembers lambdas inside composables, keyed on captures | [Strong skipping mode](https://developer.android.com/develop/ui/compose/performance/stability/strongskipping) |
| MV2 | MVVM vs MVI, Failure Modes, row 1 | "Toast re-fires after rotation → Move to `Channel<Effect>`" | Misdiagnoses the problem as state itself: repetition depends on whether consumption is represented and acknowledged. A Channel changes delivery/loss policy and is not a universal fix. The chapter's own state-first section and State Management table instead discuss advancing consumed state | [UI events](https://developer.android.com/topic/architecture/ui-layer/events) |
| SM1 | State Management, `SavedStateHandle` — Process-Death Survival | The OS kills your app for memory reasons "(Doze, low memory, …)" | Doze defers background CPU and network work to save power; it is not a memory-reclaim mechanism | [Doze and App Standby](https://developer.android.com/training/monitoring-device-state/doze-standby) |
| SM2 | State Management, Real Android Patterns 1, 2 and 5 | `@HiltViewModel class FeedViewModel(repo: FeedRepository)` (and `CheckoutViewModel`, `CheckoutWizardViewModel`) without `@Inject` | Hilt requires exactly one constructor annotated `@Inject` or `@AssistedInject`; these declarations have neither and do not compile as Hilt ViewModels | [HiltViewModel API](https://dagger.dev/api/latest/dagger/hilt/android/lifecycle/HiltViewModel.html) (constructor requirement); [Hilt ViewModels](https://dagger.dev/hilt/view-model.html) |
| SM3 | State Management, Failure Modes | Fix: "`MutableSharedFlow.update`" | `update { }` is an extension on `MutableStateFlow`; `MutableSharedFlow` has no `update` | kotlinx.coroutines API reference for `MutableStateFlow.update` |
| MO1 | Modularization Strategies, Type-Safe Navigation Across Modules | "Compose Navigation 2.7+ supports type-safe routes" | Type-safe routes arrived in Navigation 2.8.0; the Navigation chapter in this phase already says 2.8 | [Navigation releases](https://developer.android.com/jetpack/androidx/releases/navigation) (2.8.0) |
| MO2 | Modularization Strategies, Failure Modes | "`internal` classes accessible from another module — cause: modules in same package" | Kotlin `internal` is visible within one module regardless of package, so sharing a package does not expose it to another Kotlin module | [Kotlin visibility modifiers](https://kotlinlang.org/docs/visibility-modifiers.html#modules) |

| A2 | Activity, Mental Model and Architecture | An unspecified dialog appearing/dismissing pauses/resumes the activity | An in-window `Dialog` is not another Activity; its show/dismiss lifecycle does not dispatch Activity pause/resume. A dialog-themed Activity is a different case | [AOSP Dialog.show](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/app/Dialog.java); [Activity lifecycle](https://developer.android.com/guide/components/activities/activity-lifecycle) describes a new semi-transparent Activity, not every dialog |
| VM2 | ViewModel, Internal Mechanics line 61 and Production Example line 127 | `viewModelScope` is cancelled in `onCleared()` | ViewModel clears registered resources, including its scope, before invoking the `onCleared` callback | [ViewModel API: clearing sequence](https://developer.android.com/reference/androidx/lifecycle/ViewModel#onCleared()) |
| VM3 | ViewModel, Internal Mechanics line 59 | Back to exit the screen is an example of finishing the activity without qualification | On Android 12+, default Back on a root launcher activity backgrounds its task. Actual removal of the relevant ViewModel owner is the condition, as this chapter's own Answer Key 5 already says | [Android 12 Back behaviour](https://developer.android.com/about/versions/12/behavior-changes-all#back-press); [Tasks and back stack](https://developer.android.com/guide/components/activities/tasks-and-back-stack) |
| MV3 | MVVM vs MVI, Compose Integration line 208 | `collectAsStateWithLifecycle` restarts “on resume” | Its default threshold is `STARTED`; callers may explicitly select another active state | [Lifecycle-aware flow collection](https://developer.android.com/topic/libraries/architecture/coroutines#lifecycle-aware) |

The teaching example now describes a concurrent collector, not a measured UI frame | Chapter's exact `applyPromoCode` example; [StateFlow concurrency and conflation](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines.flow/-state-flow/).
