# Android Phase 8: possible errors in the original chapters

Found while writing the teaching layer for Android Phase 8 (build tooling and OS internals: the 13 chapters listed in Phase 8 of `android.md`). These are **findings for the owner's review**, not approved corrections. The original Markdown is unchanged and nothing has been added to `content/corrections-*.json`.

Each finding is flagged on its page with an **Under review** note before every affected H2 section. The note identifies the passage and says a correction is pending; it does not state the replacement. No teaching in the active blends depends on an unapproved correction.

**Verification method:** primary documentation and source (Gradle user guide and API, kotlinlang.org, developer.android.com, AOSP source, KSP `Resolver.kt`). CP1/CP2 were additionally probed with Gradle 9.7.1 (a pure-Gradle build whose root script registered `projectsLoaded` and `settingsEvaluated` actions; neither ran). No Android framework code was compiled. Checked 2026-10-25/26. Chapters with no finding: Intent Resolution, Broadcast Receivers (apart from BR1), Content Providers, Permissions and AppOps, ActivityManager, PackageManager, ART and Dalvik.

| ID | Chapter, section | Original says | Problem | Evidence |
|---|---|---|---|---|
| GB1 | Gradle and Build Systems, Why It Matters | Pressing Run executes `minifyDebugWithR8` among the build tasks | R8 runs only for build types with code optimization enabled, and Android guidance enables it for the release build, not for the debug build that Run normally installs; the list mixes a release-style task into a debug build | [Shrink, obfuscate and optimize](https://developer.android.com/build/shrink-code) |
| GB2 | Gradle, Internal Mechanics §1 and Answer Key 4 | With `api`, any modification to `UserRepo` forces recompiling A, B and C ("Avalanche Compilation"); with `implementation` the blast radius is only the declaring module | `implementation` keeps A off C's compile classpath, but whether consumers recompile depends on what changed: Kotlin incremental compilation uses classpath (ABI) snapshots, so a non-ABI change in A need not recompile dependents even through `api` | [Gradle java-library: api vs implementation](https://docs.gradle.org/current/userguide/java_library_plugin.html); [Kotlin incremental compilation](https://kotlinlang.org/docs/gradle-compilation-and-caches.html) |
| GB3 | Gradle, Internal Mechanics §3, Architecture diagram, Production Example, Answer Key 5 | The remote cache key is a hash of the input `.kt` files; a cache hit is shown as / marks the task `UP-TO-DATE`; unchanged modules are "pulled instantly from the cache" | The cache key covers the task type and classpath, input property values and plugin/build classpath, not only source files. Outputs loaded from the cache are reported `FROM-CACHE`; `UP-TO-DATE` means existing local outputs still match. Unchanged modules in an incremental build are normally up to date, not downloaded | [Gradle build cache](https://docs.gradle.org/current/userguide/build_cache.html) |
| GB4 | Gradle, Production Example | Changing one string in a 500,000-line module means Gradle "must feed all 500,000 lines into the Kotlin compiler" | Kotlin/JVM incremental compilation is on by default and recompiles only classes affected by the change. Large modules still cost more (bigger ABI blast radius, less parallelism), but not a full recompilation for each edit | [Kotlin incremental compilation](https://kotlinlang.org/docs/gradle-compilation-and-caches.html) |
| GB5 | Gradle, Failure Modes (Transitive Dependency Conflicts) | Fix: use a version catalog to centralise dependencies | A version catalog declares requested versions; it does not control which version conflict resolution selects. Gradle "may still select different versions due to dependency graph conflicts or constraints applied through platforms" | [Version catalogs](https://docs.gradle.org/current/userguide/version_catalogs.html) |
| GB6 | Gradle, Common Misconceptions and Answer Key 9 | `./gradlew clean` deletes `build/` and "destroys the local build cache" | The local build cache lives in Gradle User Home, not in `build/`; Gradle's own example runs `clean` and then loads outputs `FROM-CACHE` | [Gradle build cache](https://docs.gradle.org/current/userguide/build_cache.html) |
| GB7 | Gradle, Internal Mechanics §2 and Answer Key 3 | The configuration phase runs every single time Gradle is invoked | With the configuration cache enabled and a cache hit, Gradle reuses the stored task graph and skips configuration; the chapter's own Staff Engineer Thinking recommends this | [Configuration cache](https://docs.gradle.org/current/userguide/configuration_cache.html) |
| MM1 | Multi-Module, Gradle Settings (Type-safe project accessors) | "Still a feature preview but stable in Gradle 8+" | Current Gradle documentation calls type-safe project accessors "an incubating feature which must be enabled explicitly", and warns the implementation may change | [Type-safe project dependencies](https://docs.gradle.org/current/userguide/declaring_dependencies_basics.html) |
| MM2 | Multi-Module, Dynamic Feature Modules (use cases, "Why most apps don't need them") and Answer Key 4 | An instant-app entry point is a required/strong use case for dynamic features | Google announced that from December 2025 Instant Apps can no longer be published through Google Play and the Play services Instant APIs stop working; this is no longer a current design reason | [Google Play Instant release notes / deprecation](https://developer.android.com/topic/google-play-instant/release-notes) |
| MM3 | Multi-Module, Failure Modes ("Build cache hits drop after refactor") | Cause: "Module path changed; cache key includes path" | Gradle's documentation states that the task path is not an input to the cache key, so tasks with different paths can reuse outputs; a drop after moving modules needs another explanation (for example absolute-path-sensitive inputs) | [Gradle build cache](https://docs.gradle.org/current/userguide/build_cache.html) |
| CP1 | Convention Plugins, Pre-Commit Hooks via Convention, and Answer Key 12 | A root-project plugin registers `gradle.projectsLoaded { … }` so "every new clone of the repo gets the hooks installed automatically" | `projectsLoaded` fires before any project is evaluated; a plugin applied while the root project is being configured registers the action too late, so it does not run. The sample also executes a task action by hand outside task execution | [Gradle API: projectsLoaded](https://docs.gradle.org/current/javadoc/org/gradle/api/invocation/Gradle.html); probe with Gradle 9.7.1: an action registered from the root build script never printed |
| CP2 | Convention Plugins, Real Patterns (Pattern 4) | A `Plugin<Project>` configures local/remote build cache inside `gradle.settingsEvaluated { buildCache { … } }` | The build cache is configured in settings (or an init script). A project plugin runs after settings evaluation, so a `settingsEvaluated` action registered there does not run and the cache is never configured | [Gradle build cache: configure in settings or init script](https://docs.gradle.org/current/userguide/build_cache.html); same Gradle 9.7.1 probe |
| CP3 | Convention Plugins, Example: Android Library Convention | Comments "AGP 9+ supplies built-in Kotlin" while configuring `com.android.build.gradle.LibraryExtension` | AGP 9.0 uses the new DSL interfaces by default (`android.newDsl=true`) and no longer exposes the legacy implementation types; plugins should configure `com.android.build.api.dsl.LibraryExtension` unless the project opts out temporarily | [AGP 9.0 release notes](https://developer.android.com/build/releases/agp-9-0-0-release-notes) |
| KS1 | KSP, Common Pitfalls | Returning invalid symbols every round makes "KSP loop forever (build hangs)" | Multiple-round processing "ends when an entire round generates no new files"; if deferred symbols remain, KSP logs an error for each processor with remaining deferred symbols | [KSP multiple-round processing](https://kotlinlang.org/docs/ksp-multi-round.html) |
| KS2 | KSP, Real Patterns (Pattern 1) | An aggregating processor "scans all `@RegisterIntoMap` classes across modules" and generates one registry in `:app` | `Resolver.getSymbolsWithAnnotation` returns symbols "in the current compilation unit"; reaching dependency modules needs another mechanism, such as generated marker declarations read with `getDeclarationsFromPackage` | [KSP `Resolver.kt` KDoc](https://github.com/google/ksp/blob/main/api/src/main/kotlin/com/google/devtools/ksp/processing/Resolver.kt) |
| BD1 | The Binder, Probing Question 10 and Answer Key 10 | If system_server "crashes and reboots while your app is running", the app's proxies become unusable and can be recovered with `DeathRecipient` or API reacquisition | When system_server dies, Zygote terminates itself and with it every app process in its process group, so the app does not keep running to observe or recover those proxies; the advice applies to other remote services, not system_server | AOSP system/core commit "init: Purge empty process groups on zygote restart" (Bug 228160715): "When system_server crashes or gets killed, it causes zygote to kill itself, which in turn leads to killing all processes in the same process group (all apps)" — [mirror](https://gerrit.omnirom.org/plugins/gitiles/android_system_core/+/af64077f8366e9fcf1567c415ef167395ad2d71a%5E%21) |
| ZY1 | The Zygote, Internal Mechanics (Boot Sequence, step 8) | "`init` then launches the `SystemServer` (which is actually the very first fork of the Zygote)" | The step contradicts itself and the platform source: init starts the Zygote, and the Zygote forks system_server itself when started with `start-system-server` (`ZygoteInit.main` → `forkSystemServer`) | [AOSP ZygoteInit.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/com/android/internal/os/ZygoteInit.java); [About the Zygote processes](https://source.android.com/docs/core/runtime/zygote) |
| ZY2 | The Zygote, Historical Context | The WebView zygote exists "specifically for cloning Chrome rendering engines to prevent untrusted web code from compromising the main Zygote" | AOSP describes the WebView Zygote as "a specialized Zygote that contains libraries and resources specific to processes that run WebViews"; renderer sandboxing comes from the renderer process itself, so the stated purpose is not supported by the cited platform documentation | [About the Zygote processes](https://source.android.com/docs/core/runtime/zygote); [WebView architecture (Chromium)](https://chromium.googlesource.com/chromium/src/+/HEAD/android_webview/docs/architecture.md) |
| BR1 | Broadcast Receivers, Answer Key 8 | A background ANR occurs when `onReceive()` takes "typically >10 seconds in the background", "without offloading or calling `goAsync()`" | The documented timeouts are 10 s (10–20 s on Android 14+) for foreground-priority broadcasts and 60 s (60–120 s on Android 14+) for background-priority broadcasts. `goAsync()` does not avoid the timeout: `finish()` "is subject to the same ANR timeout as synchronous broadcast receivers" | [Diagnose and fix ANRs](https://developer.android.com/topic/performance/anrs/diagnose-and-fix-anrs) |
