# Android Phase 8 — structure before authoring

Defined 2026-10-25 after reading all 13 originals, before creating Phase 8 blends. Each page adds one concrete problem, one mechanism/failure trace, a complementary visual and three Q&A checkpoints. Original ordering, code and diagrams remain intact; no original correction is approved. Build tooling follows evidence through a build; platform chapters follow a capability, transaction or process lifetime. They do not share an artificial four-act story.

| Chapter | Problem → mechanism → consequence | Visual / step-through trace |
|---|---|---|
| Gradle and build systems | A tiny edit leaves a long wait → distinguish configuration, dependency waits and task execution from measured evidence → prioritize the critical path | Dependency chain and parallel branches; two independent compiles converging on package work |
| Multi-module | A cart edit reaches unrelated teams → map responsibilities and allowed edges → test a proposed boundary against real edits | Dependency directions versus directory nesting; route API consumed by another feature without implementation access |
| Convention plugins | Modules silently use different settings → resolve and compose capabilities → roll out one reviewed change with a representative consumer | Build logic/runtime separation; plugin ID → capabilities → consumer configuration → functional evidence |
| KSP | Generated adapter is absent → inspect processor inputs and outputs → separate generation, compilation and runtime use | Source-symbol-output boundaries; annotated declaration → processor → output artifact → ordinary compilation, avoiding disputed round details |
| Intent resolution | A verified link reaches an unauthorized order → route matching then independent input/auth validation → safe domain navigation | Routing versus authorization gates; hostile order ID rejected before internal navigation |
| Broadcast receivers | A brief callback starts work that disappears → validate/handoff/reconcile → own durable work beyond the callback | Receiver lifetime versus persistent request; duplicate hint reconciled through durable state |
| Content providers | Sharing a filesystem path fails across apps → authority/URI/grant/resource lifetime → narrow, revocable access | Provider contract map; consumer opens shared URI, reads stream, closes handle |
| Permissions and AppOps | Camera grant exists but capture fails → point-of-use capability outcome → useful denied/degraded UX | Grant / operation / feature-result gates; denied user action and intentional retry without prompt loop |
| ActivityManager lifecycle | Recents still shows a task but RAM state vanished → separate task, component and process → restore from durable owners | RAM versus persistent state; draft persisted → process reclaimed → route restored → data reloaded |
| Package manager and class loading | Install succeeds, optional route fails later → separate install registration from lazy lookup → release-like split/minification evidence | Installer versus running class loader; absent optional feature produces install/fallback state before class use |
| Binder | A method-looking call stalls a screen → follow a remote transaction and bounded service work → explicit latency/failure contract | Client/driver/service boundary; synchronous request enters busy service, returns result or error |
| Zygote | Framework setup repeats across new processes → inspect inherited mappings and private writes → distinguish process creation from application readiness | Shared readable page versus private writable page; schematic copy-on-write trace, without fixed timings |
| ART and Dalvik | The same journey changes across runs → inspect executable code availability and profiles → measure runtime state alongside app work | DEX execution modes and profile feedback; selected hot path → profile → eligible compilation → later execution |

## Evidence and exclusions

All 13 original chapters were read in full, including code, Answer Keys and Further Reading. Marker targets and Mermaid hashes were inspected through the outline tooling. Findings will be numbered in `android-phase8-findings.md`, with neutral notices before each affected H2. Correction-dependent explanatory drafts, if needed, stay in a phase-specific pending file outside active blends. No code correction is applied by adding a diagram.

Jaewoong Eum, *Manifest Android Interview* (PDF creation metadata 2025-06-16) was read at **PDF pages 48, 51, 54–64, 107–108** (15 pages, printed pages 45, 48, 51–61, 104–105). These cover service/receiver lifetimes, provider routing and initialization, and runtime compilation. Search hits elsewhere were not counted as read pages. The book is secondary framing; its broad ART AOT-only description and callback-lifetime simplifications are not adopted as current contracts. No book figure or long passage is copied.
