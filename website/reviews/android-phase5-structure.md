# Android Phase 5: structure before authoring

This plan precedes the new Phase 5 teaching files. The phase covers ten chapters on network boundaries, device permissions, hybrid content and media ownership. The original Markdown remains read-only and renders in full. This is a teaching plan, not approval of any original correction. Open questions below must be checked against primary sources before the related additions are written.

## Reader journey and coverage

| Chapter | Starting problem and learning progression | Bespoke visual / sequence | Checks and boundaries |
|---|---|---|---|
| Retrofit and OkHttp | A request works until authentication, retries and body ownership interact. Separate the service interface, adaptation/conversion and HTTP transport before judging production policy. | Trace one call through the application interceptor, an authentication challenge, a bounded follow-up and closing the response body. A separate ownership diagram identifies who owns HTTP resources. | The original Mermaid pipeline may conflate request/header construction and built-in network processing. Preserve it; hold its redraw if faithful teaching would perpetuate an error. |
| Ktor vs Retrofit | An Android team gains iOS requirements and discovers that replacing the HTTP client is not the whole migration. Compare API shape, engine configuration, cancellation, serialization and tests. | Two request paths meet at the same server; a migration stepper separates a domain-facing API from engine-specific setup and staged rollout. | Do not promise free migrations, universal binary-size wins or engine-independent features. |
| GraphQL | A profile update reaches the server but another screen shows stale cached data. Introduce operations, generated types, normalized identity and cache observations before pagination and reliability. | Follow two query results that share one normalized entity and a mutation update. Preserve the existing server/schema/client diagram when accurate. | Check Apollo response-wrapper types and operation-file comment syntax. Partial data and errors are independent axes. |
| NetworkCallback, metering, VPN and captive portal | Wi-Fi is connected but a request still cannot reach the service. Separate network presence, validation, policy and the request result. | An event timeline goes from a network becoming available through capability updates to a real request; a small policy matrix distinguishes permission to attempt from evidence of success. | Do not teach synchronous capability lookup from onAvailable as authoritative. No callback can guarantee the next request succeeds. |
| Security and Keystore | A key name exists, yet restore or biometric policy makes encrypted data unavailable. Begin with an explicit threat and key/data ownership rather than an encryption recipe. | A compact key-versus-ciphertext map and a restore/invalidation sequence. | Keep the added prose especially short. No promises of extraction-proof plaintext, automatic recovery or backup portability. |
| Device connectivity and location | A connected BLE device stops yielding useful measurements after the user leaves or permissions change. Treat connection, authorization and delivery as separate state. | Trace permission → discovery → connection → subscribed data → loss/reconnect; show location freshness versus business eligibility separately. | The book is not a source for deep BLE/camera contracts. Verify current Android permission and lifecycle rules in official docs. |
| Health Connect | A sync imports data once, then duplicates it or misses deletion/permission changes. Explain records and identity before incremental reconciliation and privacy. | A token-driven sync sequence with upserts/deletions and an expired-token recovery branch. | Separate app authorization, record ownership, feature/version availability and user revocation; do not imply a token is a permanent complete history. |
| WebView and hybrid | A checkout opens an unexpected host, keeps user cookies across a supposed isolated instance, or crashes its renderer. Start with trust and process boundaries. | A navigation decision gate and renderer-loss/replacement sequence; a compact bridge-exposure diagram explains trust at the boundary. | Check scheme/host allowlisting, frame callbacks, cookie scope and dead-WebView reuse. Hold teaching that would state an unapproved correction. |
| Media3 player architecture | A feed instantiates many players, exhausts resources and loses ownership when playback moves into the background. Distinguish player, surface, session and durable download state. | Show surface attachment moving between screens while the chosen player/session owner persists; a resource budget visual avoids fixed decoder-count assumptions. | Check DRM policy claims and distinguish a live player object from a currently allocated decoder. |
| CameraX capture architecture | Camera preview looks fine while analysis stalls and captured images differ from expectations. Explain use-case binding, backpressure and image ownership. | Show a frame arriving, being analyzed and closed before the next frame; separate Preview, ImageCapture, ImageAnalysis and video responsibilities. | Verify close-on-every-path, callback/lifecycle ownership and unsupported use-case combinations; avoid device guarantees. |

## Teaching format and evidence

Every chapter receives a short problem-first opening, a topic-specific mechanism sequence, designed visuals only where they clarify a boundary, and three reasoning checkpoints with explanations. The smallest chapters use brief captions rather than large prose expansions. Marker targets are original H2 headings, and the full original heading/code/table order is preserved by the renderer. A figure is not added merely to satisfy a count.

Manifest Android Interview by Jaewoong Eum is consulted locally for WebView and HTTP-library mental models (PDF pages 184–188 and 247–255). Its publication context is June 2025; it supplies historical teaching context, not current API authority. Current contracts come from Android Developers, AndroidX, Square Retrofit/OkHttp, Ktor, Apollo and Kotlin primary documentation. The local book is never uploaded or copied into a public artifact.

Suspected original errors are recorded by ID in `android-phase5-findings.md`. Each affected H2 receives a neutral Under review note; any proposed replacement teaching belongs in `pending-android-phase5-teaching.blend`, not active content. Findings remain unapproved. Android examples are source-reviewed, not claimed compiled or run. After authoring, an isolated render checks markers, stepper JSON and original preservation; another agent reviews technical accuracy before the next phase proceeds.
