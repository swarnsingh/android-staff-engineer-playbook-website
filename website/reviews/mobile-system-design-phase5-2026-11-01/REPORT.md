# Mobile System Design Phase 5 publication review

This release publishes the six chapters in Phase 5 of the existing guided reading path: Google Maps / Location System, Ride-Hailing, Payment Flow, Play Billing and Subscriptions, Stock Trading App, and YouTube / Video Streaming. Earlier phases stay in their existing order. Phase 6 remains linked to the source repository until its own publication milestone completes. This is a lean reader release: the complete reviewed chapters, designed figures, chapter introductions, and short interview recaps. It does not introduce a new reader component or a second design system.

The source corrections were reviewed through original playbook PR #70 and merged as c7427001ab3ef5b5e1ffd5d9fff535ba23115840. The snapshot used here is source main at 400a7d7dd85c962b6b2d6d856712ca316a11edc8, which also includes the separately merged Phase 6 corrections. Only the six Phase 5 files were copied for this milestone. Each copy was compared byte-for-byte against that commit, and its SHA-256 was updated in source-snapshot.json. No original passage was rewritten as website work. The source repository and the website snapshot retain separate ownership and an explicit commit trail.

Fourteen FigureMap models replace all Mermaid pictures in these chapters. The original Mermaid remains available as preserved source beside the designed figure. The models use the shared client, execution, storage, queued-work, and neutral roles; visible border patterns and labels supplement colour. Every relationship has a label, owner boundaries distinguish app and backend responsibilities, and captions state the point of each figure. The payment sequence preserves the order of intent creation, provider confirmation, signed webhook and canonical status lookup. State diagrams retain their cancellation, expiry and recovery branches. Layout is automatic and all visual styling comes from the shared design system.

Five chapters use the existing interview-walkthrough component, which derives its timeline and practice prompts from the original numbered headings. Play Billing uses the normal chapter layout because its source is organised around a subscription lifecycle rather than the standard twelve-section interview. Its content is not forced into missing clarifying-question or follow-up sections. All original answers remain visible; this release does not enable a practice mode that hides the chapters. Added recaps are labelled as website teaching material and stay short enough to serve as revision aids.

Validation includes the pending build during preparation, a final build without pending figures, model validation, browser frame checks, the website CI command and the six publication audits. Static preservation checks cover 191 pages and 24,502 original units in order. Model checking covers 150 FigureMaps across the site with no model errors. Desktop frame checking covers 185 chapter pages, 149 figures, 138 relationship maps and 3,056 labels without reported framing problems. Website CI passes its fifteen website tests, thirty-one documentation checker tests, documentation gate and ten browser-script syntax checks. The audit JSON files alongside this report record the complete current reader rather than only the newly published pages.

A focused visual inspection used Chromium at 1440 and 375 CSS pixels for the payment, trip-state and billing figures. Those pages did not create whole-page horizontal scrolling. Wide two-dimensional figures keep their readable labels inside their own bounded scroll viewport on phones. The full audit adds the existing preservation, preferences, motion, refinement, navigation and negative-fixture checks. This is browser emulation, not a physical Android phone or a screen-reader certification. Other browser engines were not exercised during this release.

The source examples remain educational pseudocode. This publication does not claim that payment confirmation, broker execution, Play entitlement verification, foreground-service restart, GPS sampling or DRM renewal ran on a device or live backend. Those limits remain material even when the website checks pass. The reviewed source fixes and official references support the teaching content; the browser evidence supports preservation and reader behaviour. Publication requires the fresh audit results, a passing publication gate, green PR checks and a successful GitHub Pages deployment.
