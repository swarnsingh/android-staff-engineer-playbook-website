# Distributed Systems source scope notes

All 12 chapter snapshots and the index are exact bytes from approved source `fb8354edb079e901edf18710ca9388a124712a5b`. These notes describe remaining simplifications; they do not approve or apply chapter corrections.

- **CAP product sketch:** the preserved architecture diagram labels products CP/AP and depicts DynamoDB with configurable W/R. The teaching guide and redraw instead require checking the actual operation/configuration contract. DynamoDB documents read modes and scopes, not a generic client-selected quorum API. Quorum intersection alone is not a linearizability proof. [DynamoDB read consistency](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadConsistency.html), [Gilbert and Lynch](https://groups.csail.mit.edu/tds/papers/Gilbert/Brewer2.pdf).
- **Consistency acknowledgement trace:** waiting for all shown followers is one example, not a universal linearizability requirement. The added guide distinguishes the history contract from implementation choice. [Raft](https://raft.github.io/raft.pdf).
- **Idempotency:** a persisted key alone does not extend the backend's retention contract or make an external effect part of a local database transaction. The walkthrough explicitly models a local ledger and an illustrative late retry after pruning. No payment integration is claimed. [Stripe API v1 replay contract](https://docs.stripe.com/api/idempotent_requests).
- **CRDT short answers:** answer 1 describes classical op-based requirements, answer 4's UX preference is contextual, and answer 10 must not imply convergence preserves every user's intent. The scoped guide names those limits. The new counter trace compares per-actor contributions with an intentionally incorrect scalar-max merge. It is a teaching model, not a runtime CRDT implementation. [CRDT study](https://www.lip6.fr/Marc.Shapiro/papers/2011/Comprehensive-CRDTs-RR7506-2011-01.pdf).
- **Consensus short answers:** an uncommitted entry can survive or be overwritten; a future leader need not be a particular old-majority member, but eligible voting/log rules preserve committed entries. Current-term majority counting does not apply directly to arbitrary older entries. Linearizable reads need their protocol procedure. The added answer guide and current-term example retain these distinctions. [Raft §§5.4 and 8](https://raft.github.io/raft.pdf).
- **Vector-clock ownership:** the receiving process learns an event without changing the causal version of the received write. The walkthrough preserves those write versions and presents siblings for concurrent inputs. Stable replica identities and safe retirement remain required; metadata pruning does not have a universal time-only rule. [Dynamo version reconciliation](https://www.allthingsdistributed.com/files/amazon-dynamo-sosp2007.pdf).
- **Fencing:** the resource must enforce the epoch with the protected effect. Cancelling an app worker or changing a lease alone does not fence an external destination. The walkthrough states an illustrative atomic enforcement contract. [Chubby sequencers](https://research.google.com/archive/chubby-osdi06.pdf).
- **Streaming:** partition order is not global order or a guarantee that concurrent downstream work finishes in append order. The guide distinguishes log offsets, API continuation and entity revisions. [Kafka design](https://kafka.apache.org/41/design/design/).
