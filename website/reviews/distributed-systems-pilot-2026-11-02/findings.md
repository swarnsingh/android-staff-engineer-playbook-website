## Claims needing contextual limits

- **Historical UDP sentence:** sending a datagram once does not prevent network duplication. The source's at-most-once label requires an application contract. [RFC 8085 §3.3](https://www.rfc-editor.org/rfc/rfc8085.html#section-3.3) explicitly discusses duplication, loss and reordering. The added note appears before Historical Context rather than restating the broad source sentence.
- **Overview, comparison table and reliability summaries:** unconditional “never lost” wording omits retention, eventual execution/recovery and the failure envelope. First Principles and the source retry fragment now contain those qualifications, but the summaries remain broader. The added note before Tradeoffs carries the assumptions and avoids treating latency rankings as universal measurements. [Kafka's design](https://kafka.apache.org/41/design/design/) separates producer durability from consumer processing policy.
- **Acknowledgement ownership:** publisher confirmation, consumer acknowledgement and an application result confirm different boundaries. The prototype follows an application result after a local order commit. Its retry policy must not be read as RabbitMQ publisher confirms reaching the original producer from a consumer. [RabbitMQ's acknowledgement contract](https://www.rabbitmq.com/docs/confirms) distinguishes these independent mechanisms.
- **Exactly-once wording:** blanket statements in Staff Engineer Thinking and Common Misconceptions need the same scope as the more specific Production Example. [Pub/Sub documents a regional pull-subscription guarantee](https://docs.cloud.google.com/pubsub/docs/exactly-once-delivery), and Kafka defines its transactional scope. Neither establishes an external payment effect. The local order transaction is explicitly separate from an outbox relay and downstream service; [the outbox pattern](https://github.com/aws-samples/transactional-outbox-pattern) still requires handling duplicate messages.
- **Answer 4:** persisted client identity alone is insufficient. The backend must enforce account and payload binding, concurrency-safe capture and retention. **Answer 7:** no finite TTL proves safety for unbounded offline retries; reconcile after the retention horizon. [Stripe's API v1 replay contract](https://docs.stripe.com/api/idempotent_requests) explains parameter checking and reuse after pruning.
- **Answers 6, 8 and 10:** a DLQ is one bounded failure disposition, not the only possible policy; 2PC/idempotency costs depend on the actual participants and invariants; and durable notification creation differs from push receipt/display. The Q&A guide covers scoped guarantees and push limits, while these broader original answers remain an owner review consideration. [FCM lifetime documentation](https://firebase.google.com/docs/cloud-messaging/customize-messages/setting-message-lifespan) describes expiry and delayed delivery.
